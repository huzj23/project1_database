## 1. 冻结项 A：转盘（Turntable）

### 1.1 资产

| 项 | 值 |
|---|---|
| **路径** | `assets/objects/turntable/` |
| **几何** | URDF `<cylinder radius="0.30" length="0.022"/>` |
| **半径** | **0.30 m**（直径 0.60 m） |
| **厚度** | 0.022 m |
| **碰撞** | **精确圆柱原语**（非凸包分解） |
| **质量** | 加载后实测 1.0 kg |
| **许可证** | CC0（本项目生成，无第三方内容） |
| **生成脚本** | `tools/make_turntable_asset.sh`（`TT_RADIUS` / `TT_THICK` 可传参） |

> **为何程序化生成**：GSO 1033 个物体、Poly Haven 521 个模型中**均无转盘**（只有 DVD 碟片、花盆底碟、托盘）。且 URDF 圆柱碰撞是精确原语，旋转平滑；扫描网格需凸分解，转动会一格一格跳。

### 1.2 物理驱动方式（冻结）

```text
转盘 = 动力学体（static=False）        ← 必须，见下方陷阱 1
每物理步：
  1. _cp, cq = getBasePositionAndOrientation(disc)
  2. resetBasePositionAndOrientation(disc, [TX,TY,DZ], cq)   # 钉位置，朝向原样传回
  3. resetBaseVelocity(disc, [0,0,0], [0,0,OMEGA])           # 这就是"电机"
  4. stepSimulation()
```

**"物体绕圈"是接触+摩擦的结果，不是脚本写死的路径。**

### 1.3 实测验证（240 Hz 步进，ω = 0.9 rad/s）

| 帧 | 物体半径 | 物体角度 |
|---|---|---|
| 00 | 0.170 m | +1.9° |
| 06 | 0.170 m | +21.3° |
| 12 | 0.170 m | +40.6° |
| 18 | 0.170 m | +59.9° |
| 24 | 0.170 m | +79.2° |

**半径恒定 0.170 m**（绕轴公转而非滑出）+ **角度线性递增**（匀角速度）= 物理正确。

另在 0.5 rad/s 下测 **滑移比 0.99**（物体以转盘 99% 的速度被携带）。

### 1.4 材质（冻结）

**用测量选型，不靠猜。** 同一转盘渲染四种木材：

| 木材 | R/B | 木纹 (Laplacian var) | 判定 |
|---|---|---|---|
| `cherry_veneer` 樱桃木 | 1.40 | 14.8 | ❌ 偏淡 |
| `american_walnut_veneer` 胡桃木 | 1.05 | 57.2 | ❌ 发灰 |
| **`dark_wood`** | **2.00** | **49.8** | ✅ **采用** |

成品实测 **R/B = 1.83、R/G = 1.58**，落在红木区间（R/B 1.6–2.6、R/G 1.3–1.8）。

### 1.5 摆放（冻结）

| 项 | 值 |
|---|---|
| 承载面 | `frl_apartment_table_01` 桌面 |
| 桌面中心 | **(0.41, 0.17)** |
| 桌面高度 | **z = 0.758 m** |
| 桌面跨度 | 1.40 × 0.85 m |
| 转盘中心 z | 0.771 m（= 0.758 + 0.011 + 0.002） |

> **半径为何是 0.30 m**：最初用 0.55 m（直径 1.1 m），盘子**悬在 0.85 m 宽的桌外**，一眼就假。

### 1.6 ❌ 勿用（已排除的错误做法）

| # | 错误做法 | 现象 | 正确做法 |
|---|---|---|---|
| 1 | `static=True` | Kubric 传 `useFixedBase=True`，**转盘被焊死**，永远不转 | 必须 `static=False` |
| 2 | `changeDynamics(mass=0)` | PyBullet 里 mass=0 = **静态体**，设了角速度也不动 | 保持动力学体，每步重设角速度当"电机" |
| 3 | 每步重置朝向为单位四元数 | 转盘**视觉上不转**（物体仍会爬行） | 朝向原样传回，让它自己积分 |
| 4 | 每步"传送"转盘位姿 | 接触流形被反复重置，摩擦**完全无法建立**（滑移比 0.00） | 只钉位置，不重置朝向 |
| 5 | 按视频帧步进 | 一切看起来**慢 10 倍**（Kubric 客户端按 1/240 s 步进） | 每视频帧步进 `physics_fps / video_fps` 次 |
| 6 | 半径 0.55 m | 悬在桌外 | 0.30 m |

### 1.7 ⚠️ 关键帧铁律（影响全局）

**Blender 不会自己动——必须把物理轨迹转录为关键帧。**

未转录时，渲染 4 帧得到的是**四个字节完全相同的 PNG**：

```text
mahogany_f00.png  MD5=DA6B7B8E482F64C9
mahogany_f08.png  MD5=DA6B7B8E482F64C9
mahogany_f16.png  MD5=DA6B7B8E482F64C9
mahogany_f24.png  MD5=DA6B7B8E482F64C9
像素差 max=0  mean=0.000
```

**转录代码（冻结模板）**：

```python
for f, (ap, aq) in enumerate(traj):          # traj 来自 PyBullet
    bpy.context.scene.frame_set(f)           # 注意：kb.Scene 没有 frame_set
    ao.location = ap
    ao.rotation_mode = "QUATERNION"
    ao.rotation_quaternion = (aq[3], aq[0], aq[1], aq[2])
    ao.keyframe_insert("location", frame=f)
    ao.keyframe_insert("rotation_quaternion", frame=f)
```

转录后 4 帧真正不同：

| 对比 | 最大像素差 | 变化像素数 |
|---|---|---|
| f08 vs f00 | 179 | **1,240,023** |
| f16 vs f00 | 186 | **1,304,644** |
| f24 vs f00 | 186 | **1,413,039** |

> **这仍是"绝不用预先规定的轨迹"**：轨迹由物理引擎（接触+摩擦）产生，我们只把**结果**转写让 Blender 回放。

## 4. 室外地面接缝问题：根因与结论（2026-09-22）

### 4.1 问题

用户反馈：**物体所在的地面与场景背景仍有突兀感**。

### 4.2 三个被实测排除的猜测

| 猜测 | 实验 | 结果 | 结论 |
|---|---|---|---|
| "HDRI 没有地面，我们铺的替代了它" | 直接读 4K HDR 全景 | **地平线在 ≈0°**（kloppenheim +1.05°、german_town +1.76°、autumn_park −2.11°） | ❌ **HDRI 自带地面**：等距圆柱全景的**下半部分就是地面影像** |
| "我们的平面太小，露出了全景地面" | 平面 14 m / 120 m / 800 m 三档对比 | 跳变 **+50.7 / +51.9 / +44.2**，几乎不变 | ❌ **尺寸无关** |
| "我们的平面根本没显示出来" | 把地面涂成**品红色** | 品红占下半屏 **99.38%** | ❌ **我们的平面确实可见，且已遮住全景地面** |

### 4.3 真正的原因

逐行对比"有地面 / 无地面"两张渲染图：

```
row 240-340 :  有地面 lum == 无地面 lum   差值 +0.0   ← 我们的平面在这些行完全不可见
row 360+    :  开始出现差异                          ← 我们的平面从这里才开始
最锐利跳变   :  row 317 (grad 28.69) = 地平线本身，不是平面边缘
```

**根本原因是几何上的不可能**：

> **HDRI 是"位于无穷远的 2D 图像"**——它没有视差，且它的地面已经把**拍摄时的透视关系**烘焙进去了。我们用一块真实的 3D 平面、用我们的相机去渲染，**永远无法与一张画出来的 2D 地面严丝合缝**。

这不是参数没调好，而是**方法本身的边界**。继续调尺寸/亮度/材质都是徒劳。

### 4.4 正确的解法：影子捕捉地面（shadow catcher）

**不要再试图让两块地面匹配——只保留一块：全景自带的那块。**

平面仍然需要（物体要站、要投接触阴影），但把它改成 **shadow catcher**：

```python
go = ground.linked_objects[renderer]
go.is_shadow_catcher = True      # Cycles：对相机不可见，但仍接收阴影
```

这样观众看到的地面**就是 HDRI 自带的地面**，物体的接触阴影**正确落在它上面**，接缝从原理上消失。

**实测效果**：

| 环境 | 可见地面 DIFF | **shadow catcher DIFF** | 改善 |
|---|---|---|---|
| autumn_park | +13.9 | **−1.4** | ✅ 几乎完美 |
| ballawley_park | +16.8 | **+5.3** | ✅ 明显改善 |
| kloppenheim_02 | +13.6 | **+8.9** | ✅ 改善 |
| german_town_street | +51.9 | +57.6 | ⚠️ 指标失效（见下） |
| orlando_stadium | −116.0 | −60.0 | ⚠️ 指标失效（见下） |

> **诚实说明**：german_town_street 与 orlando_stadium 两行的"地平线下方"数值在两种模式下**完全相同**（如 173.1 vs 173.1），说明我的地平线检测在这两张图上**定位到了错误的行**（大概率是远景建筑/看台的亮边，而非地平线）。这两个数字**不可信，需要人眼判断**，不能当作"阴影捕捉无效"的证据。

### 4.5 附带发现：私自加太阳光违反了铁律四

排查中发现 `render_outdoor*.sh` **私自加了一盏 DirectionalLight（强度 2.6）**。

- 这盏灯照亮**我们的平面**，但**照不到全景**（全景地面是烘焙进 HDRI 的，自带曝光）
- 结果：我们的地面被一个太阳照，全景地面被另一个"太阳"照——**两块地面两套曝光**
- 这**直接违反铁律四**（"只听场景作者光照，不私自加太阳光"）

**改为 HDRI-only 光照**（`strength=1.0`，让 HDRI 同时负责照明与背景）后，两块地面由**同一环境**照亮，亮度自然一致。实测对比：

| 环境 | 加太阳 | HDRI-only |
|---|---|---|
| ballawley_park | +95.3 | **+86.9** |
| orlando_stadium | +42.4 | **+36.3** |
| german_town_street | +78.5 | +78.5 |

### 4.6 冻结结论

| 项 | 结论 |
|---|---|
| **HDRI 是否自带地面** | ✅ **是**，下半部分即地面，地平线 ≈0° |
| **我们是否错误替换** | ❌ **否**，我们的平面覆盖了 99.4% 下半屏 |
| **突兀感的根因** | **HDRI 是无视差的 2D 图像，无法与真实 3D 平面几何对齐**（方法边界，非参数问题） |
| **正确解法** | **shadow catcher**：保留全景地面，平面改为只接收阴影 |
| **光照** | **只用 HDRI**（HDRI-only），删除私自添加的太阳光（铁律四） |
| **仍需人眼确认** | german_town_street / orlando_stadium 的自动化指标不可信 |
