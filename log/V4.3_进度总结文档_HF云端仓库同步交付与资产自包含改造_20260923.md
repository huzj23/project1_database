## 2 ⚠️ 上传前发现的重大风险：直接用学长脚本会**删掉学长的 11 项资产**

这是本次最重要的发现。学长的 `sync_hf_assets.py` 的 `upload_assets()` 有两处**整文件覆盖**：

```python
manifest = build_remote_manifest(project_root, records, repo_id)
api.upload_file(path_or_fileobj=str(manifest_path), path_in_repo="assets_manifest.json", ...)
api.upload_file(path_or_fileobj=str(card_path),     path_in_repo="README.md", ...)
```

而 `build_remote_manifest()` **只从传入的 records 重建清单，从不读取远端清单**：

```python
def build_remote_manifest(project_root, records, repo_id=DEFAULT_REPO_ID):
    assets = []
    for record in records:      # 只有本次选中的资产
        ...
    return {"schema_version": 1, "repository": repo_id, "assets": assets}
```

**后果**：若直接执行 `sync_hf_assets.py upload --asset-id <我们的3个>`，远端清单会被替换成只含我们 3 项的版本，**学长 11 项资产的记录（195 个文件、1960.94 MB）将全部消失**。

### 2.1 我的处理方式：合并式上传

新增驱动 `tools/hf_additive_upload.sh`，逻辑为：

1. 先下载远端清单，**保留其全部条目**
2. 用学长自己的 `_payload_files()` / `_sha256()` 生成我们的条目（口径与学长一致）
3. **合并**：`[远端非我们的条目] + [我们的 3 项]`，并断言"没有任何远端资产被丢弃"
4. 只上传我们的 3 个目录 + 合并后的清单 + 数据集卡片
5. 上传后**重新读取远端**证明学长 11 项仍在

上传前后实测：

```
上传前 remote manifest: 11 assets
合并后: 14 assets
  preserved from remote: ['basketball_court','classroom','street','food_apple','food_lime',
                          'food_lychee','special_coffee_cup','sphere_baseball',
                          'sphere_basketball','sphere_football','sphere_volleyball']
  added by us          : ['special_plush_elephant','replicad_apartment','turntable']
  no remote asset is dropped: OK

上传后: 14 assets
  mentor's 11 still present: True
  ours present            : True
```

> 备份：上传前的远端清单与 README 已存至 `tmp/hf_backup/`（`REMOTE_assets_manifest.json` 45,904 B、`REMOTE_README.md` 1,781 B），可随时回滚。

### 2.2 顺带修正清单的一个陈旧字段

远端清单的 `repository` 字段原为 `TLEphage/physics-video-assets`（旧仓库名），已修正为实际的 `physics-video-lab/physics-video-assets`。

### 2.3 README 覆盖是安全的

## 4 关键改造：让资产在下载后**真正可用**（自包含 PBR）

### 4.1 发现的问题

`turntable` 声明 `visual.material: {pbr: dark_wood}`，而 `materials.py` 从**仓库之外**的共享库解析：

```python
DEFAULT_PBR_ROOT_RELPATH = Path("..") / ".." / ".." / "models" / "pbr_textures"
```

该目录 623 MB，位于 `<workspace>/models/pbr_textures`，**不在仓库内**。因此同学 `git clone` + `sync_hf_assets.py download` 之后**没有这些贴图**，`apply_declared_material()` 会抛 `FileNotFoundError`，资产**不可用** —— 直接违背"确保其可用 / 后面直接用就行了"的要求。

### 4.2 改造方式（遵循原有声明式设计，不改学长脚本）

| 文件 | 改动 |
|---|---|
| `src/physim/assets/__init__.py` | `MaterialSpec` 新增 `textures`（相对资产的贴图目录）与 `asset_dir`；`_material()` 解析 `textures` 并**校验不逃逸资产目录** |
| `src/physim/render/materials.py` | `find_texture_dir()` 新增 `spec` 参数：**先查资产内 `textures`，再回退共享库** |
| `assets/objects/turntable/asset.yaml` | 新增 `textures: visual/textures/dark_wood` |
| `assets/objects/turntable/visual/textures/dark_wood/` | 放入 3 张 4k 图（与共享库**逐字节相同**，sha256 已验） |

**向后兼容**：`spec` 为可选参数，`textures` 缺省为 `None`，其余资产行为完全不变。

## 9 遗留事项与风险

| # | 事项 | 说明 |
|---|---|---|
| 1 | **`CC BY-NC 4.0` 禁商用** | `replicad_apartment` 不可用于商业用途；若本项目视频用于商业产品或演示，**需替换该场景** |
| 2 | **`CC BY-SA 4.0` ShareAlike** | 若数据集被视为衍生作品并**对外发布**，须以同样许可发布；私有仓库内部分享通常不触发 |
| 3 | **仓库必须保持私有** | 学长卡片明确要求"不得改为公开"。`UNKNOWN` 资产（学长 6 项）更严禁分发 |
| 4 | 学长 11 项资产的 `verify` 缺失 | 100 个文件缺失，**既有问题**，非本次引入；其大文件从未镜像到本服务器 |
| 5 | 学长脚本的覆盖风险 | 建议向学长反馈：`upload` 应改为**合并**而非重建清单，否则任何人单独上传自己的资产都会抹掉他人记录 |
| 6 | 分段层（segmentation）缺陷 | 转盘视频的分段标签只有 `[0,3]`，**演员无自身标签**（标签 1、2 从不出现）。**既有缺陷**，与本次改动无关，建议单独排查 |
| 7 | 本机 DNS 污染 | 本机 `huggingface.co` 解析到 Dropbox/Meta 地址，**本机无法直连 HF**；所有 HF 操作均经服务器完成 |
