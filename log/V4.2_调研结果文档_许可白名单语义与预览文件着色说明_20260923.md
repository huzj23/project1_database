## 1 问题一：许可白名单——我们的范围是**更小**（更严），不是更大

### 1.1 先分清两个完全不同的概念

| 概念 | 含义 | 谁决定 |
|---|---|---|
| **资产自身的许可**（`asset.yaml` 的 `license:`） | 这份素材**法律上允许你做什么** | 原始作者（Google / Meta / Poly Haven） |
| **上传白名单**（`sync_hf_assets.py --allowed-license`） | 学长脚本**愿意自动上传哪些许可的资产** | 学长写的默认值，**可以改** |

**关键**：白名单不是"许可范围"，而是**一道自动化的谨慎闸门**。它变严不影响你合法使用资产，只影响脚本是否肯替你上传。

### 1.2 三种许可的实际自由度对比

| 许可 | 商用 | 可修改 | 再分发 | 传染性（copyleft） | 义务 |
|---|---|---|---|---|---|
| **CC0-1.0** | ✅ | ✅ | ✅ | 无 | 无（可不署名） |
| **CC BY 4.0** | ✅ | ✅ | ✅ | 无 | 署名 |
| **CC BY-SA 4.0** | ✅ | ✅ | ✅ | **有**：衍生作品须用**同样许可**发布 | 署名 + **相同方式共享** |
| **CC BY-NC 4.0** | ❌ **禁止商用** | ✅ | ✅（非商用） | 无 | 署名 + **非商用** |

**所以"范围"是这样变的**：

- 从 **CC0-1.0** 到 **CC BY-SA 4.0**：**更小/更严**。多了"必须署名"和"衍生作品必须同样开源"两条义务。
- 从 **CC0-1.0** 到 **CC BY-NC 4.0**：**更小/更严**。多了"必须署名"，且**明确禁止商用**。

**结论：我们的两个资产许可范围都比 CC0 更小（限制更多）。白名单报错正是因为这个——脚本发现许可比它默认愿意自动处理的更严格，所以拒绝，而不是说我们不能用。**

### 1.3 学长脚本的行为（实测，不是推测）

用学长自己的 `sync_hf_assets.py` 实跑，证据如下：

**默认（不传 `--allowed-license`）**：
```
$ python scripts/sync_hf_assets.py list --asset-id special_plush_elephant
RuntimeError: Requested assets are not redistributable under the configured
license allowlist: special_plush_elephant (CC BY-SA 4.0)

$ python scripts/sync_hf_assets.py list --asset-id replicad_apartment
RuntimeError: ... replicad_apartment (CC BY-NC 4.0)
```

**显式声明许可后（成功）**：
```
$ python scripts/sync_hf_assets.py list --asset-id special_plush_elephant \
    --allowed-license "CC BY-SA 4.0"
UPLOAD	special_plush_elephant	CC BY-SA 4.0	47711679

$ python scripts/sync_hf_assets.py list --asset-id replicad_apartment \
    --allowed-license "CC BY-NC 4.0"
UPLOAD	replicad_apartment	CC BY-NC 4.0	57762292
```

**永远不能放行的许可**（代码硬性拒绝，`forbidden_license_labels`）：
```
$ python scripts/sync_hf_assets.py list --allowed-license "UNKNOWN"
RuntimeError: Unknown or absent licenses can never be upload-allowed: UNKNOWN
```

**学长自己资产的默认结果**：
```
UPLOAD	classroom	CC0-1.0	254954
UPLOAD	food_lime	CC0-1.0	36795
UPLOAD	food_lychee	CC0-1.0	36850
UPLOAD	sphere_baseball	CC0-1.0	940
BLOCKED	basketball_court	UNKNOWN
```

### 1.4 学长脚本的设计逻辑（读代码得出）

`DEFAULT_ALLOWED_LICENSES = ("CC0-1.0",)` 是**保守默认**，理由是：

1. 仓库是**私有工作档案**，但要能被组内直接同步进项目使用；
2. CC0 是**唯一无需署名、无任何附加义务**的许可，自动上传它**不可能产生合规风险**；
3. `UNKNOWN` 被硬性拒绝，因为**许可不明就不能分发**（学长文档原话："源许可证未知时可以进行本地验证，但必须标记 `license: UNKNOWN`，不得分发或上传该大文件"）；
4. 白名单**可显式放宽**——这就是给我们这种"许可已知且允许再分发"的资产准备的入口。

### 1.5 对我们的实际影响

| 资产 | 许可 | 能否上传私有仓库 | 需要什么 |
|---|---|---|---|
| `special_plush_elephant` | CC BY-SA 4.0 | ✅ 可以 | `--allowed-license "CC BY-SA 4.0"` |
| `replicad_apartment` | CC BY-NC 4.0 | ✅ 可以 | `--allowed-license "CC BY-NC 4.0"` |
| `turntable` | CC0 | ✅ 默认即可 | 无 |

**三点必须注意**：

1. **CC BY-SA 的传染性**：小熊是 ShareAlike。如果我们的**数据集**被视为"衍生作品"并对外发布，需以同样许可发布。**私有仓库内部分享**通常不触发，但**对外发布要谨慎**。
2. **CC BY-NC 的禁商用**：公寓**不可用于商业用途**。若本项目的视频将来用于商业产品或商业演示，**需替换该场景**。
3. **仓库必须保持私有**：学长数据集卡片明确要求——"不得通过把数据集改为公开来使其可访问"。CC BY-NC 资产进入公开仓库会直接违反许可。

### 1.6 ⚠️ 顺带发现：GSO 源文件的许可标注不一致

小熊的来源存在**两种互相矛盾的许可声明**：

| 来源 | 声明 |
|---|---|
| 单文件 MTL 头（`visual_geometry.mtl`） | "Creative Commons **Attribution 4.0**"（= CC BY 4.0，**无** ShareAlike） |
| 物体自带 `data.json` | `"license": "CC BY-SA 4.0"` |
| 集合 `GSO.json` | `"license": "CC BY-SA 4.0"` |

**我采用了更严格的 CC BY-SA 4.0**（与集合元数据、物体元数据一致，且更保守）。这是"就高不就低"的选择，已在 `license/SOURCE.md` 中记录该不一致，并注明 ShareAlike 义务。

> 这与我们的**其他 5 个 GSO 资产**保持一致（它们也都记为 CC BY-SA 4.0），所以整个 GSO 系列的许可口径统一。

## 2 问题二：预览 `.blend` 打开没有颜色——**文件是好的，是 Blender 的显示模式问题**

### 2.1 诊断结论（实测，不是猜测）

材质**完全正常**，实测数据：

| 检查项 | 实测值 |
|---|---|
| 材质总数 | 94 |
| **含图片贴图的材质** | **89** |
| 公寓网格的材质 | 91 个 |
| 贴图打包 | **91 张，全部已打包（`unpacked: 0`）** |
| 转盘材质 `pbr_dark_wood` | `use_nodes=True`，**8 个节点** |
| └ 三张贴图 | `dark_wood_diff_4k.jpg`(4096²) + `_rough_4k` + `_nor_gl_4k`，**全部 packed** |
| └ Base Color | `is_linked=True`（已接贴图） |
| 场景相机 | `camera__side_perpendicular` ✅ |
| 渲染引擎 | `CYCLES` ✅ |
| 7 盏作者灯 + `environment_world` | ✅ 均在 |

**真正原因**：文件的视口保存为 **SOLID 着色模式**：

```
screen='Layout'  shading.type=SOLID  color_type=MATERIAL  light=STUDIO
```

**SOLID 模式只显示材质的"平色"（Viewport Display 颜色），完全不读取节点树**。所以 PBR 木纹和小熊贴图都不会出现，整个场景是一片没有纹理的灰 —— 这不是文件坏，是**显示模式选择**。

### 2.2 三种解决办法

**办法一：手动切换（最快，1 秒）**

打开文件后，在 3D 视图右上角把着色模式从 **Solid（第一个球）** 切到 **Rendered（最后一个球）**。或按快捷键：

| 快捷键 | 模式 | 效果 |
|---|---|---|
| `Z` → `6` | **Rendered** | **完整 PBR 材质 + 作者灯光**（推荐） |
| `Z` → `2` | Material Preview | 材质预览（用 studio HDRI，不是场景灯光） |

**办法二：用我新做的彩色版本（推荐，双击即有颜色）**

`outcomes/_hf_preview/replicad_apartment-special_plush_elephant-preview-COLOR.blend`

我把每张贴图的**平均颜色烘焙进材质的 Viewport Display 颜色**，SOLID 模式下也能看到接近真实的颜色。实测：

| | 原文件 | COLOR 版本 |
|---|---|---|
| `pbr_dark_wood` 视口颜色 | `(0.8, 0.8, 0.8)` 灰 | **`(0.393, 0.171, 0.099)` 木棕** |
| 非默认视口颜色的材质 | 0 | **92 / 94** |
| 打包贴图 | 91/91 | 91/91 |

**已在你本机 Blender 5.2.2 实测**：视口颜色持久保存，打开即是彩色。

**办法三：直接渲染看质量**

`STILL_wide_final.png` / `STILL_closeup_final.png` 就是**生产设置**（1920×1080、Cycles CPU、24 spp、去噪、Filmic/Medium High Contrast）渲出的成品，与已交付视频**逐像素一致**（mean diff 0.000/255）。看质量直接看这两张图最准。

### 2.3 烘焙没有影响渲染质量（已证明）

我只改了 `diffuse_color`（SOLID 显示用的平色），**节点树一个字节没动**。实测两个文件渲染结果**完全相同**：

| | 原文件 | COLOR 版本 |
|---|---|---|
| 渲染均值 | 0.2642 | **0.2642** |
| 木色像素占比 | 35.56% | **35.56%** |
| 木色像素 RGB | [0.252, 0.147, 0.108] | **[0.252, 0.147, 0.108]** |
| 节点贴图 | 3 张全在 | 3 张全在 |
| Base Color 已连接 | True | True |

**结论**：COLOR 版本可以放心用于目检，渲染质量与原文件一致。

### 2.4 一个技术说明

我曾尝试直接把视口改成 RENDERED 后保存，但从 Blender 3.4.1 的 `--background` 模式保存时该设置**不落盘**（内存中读回是 RENDERED，重新打开又变回 SOLID）。实测确认这不是"Load UI"开关的问题（`use_load_ui` 已为 True 仍如此）。所以改用了**烘焙视口颜色**这个确实能持久化的方案。
