## 1. 重大缺陷一：铁律四违规（已修复）

### 1.1 发现经过

T1 首条 rolling 渲染的 `RENDER_DIAGNOSTICS` 打印出：

```
environment_lighting_source': 'asset_fallback'
environment_light_count': 1
environment_light_types': ['AREA']
environment_authored_world': None
```

`asset_fallback` 意味着渲染器**没有找到场景作者的光照**，转而使用**它自己硬编码的一盏 AREA 灯**（`blender_backend.py` 第 266–288 行，intensity 1100，位置 (0, -2, 10)）。

这盏灯**是我们加的，不是场景作者的**，直接违反铁律四。

### 1.2 根因（命名不匹配）

| 位置 | 集合名 | 世界名 |
|---|---|---|
| `scene.blend` 实际 | `authored_lighting` | `World` |
| 渲染器 `_append_authored_lighting()` 查找 | `environment_lighting` | `environment_world` |
| 项目规范化脚本 `scripts/prepare_visual_asset.py`（第 26–27 行）规定的产出名 | `environment_lighting` | `environment_world` |

`scene.blend` 是**直接从 ReplicaCAD 导出**的，**没有经过项目自己的规范化脚本**，因此集合保留了源名 `authored_lighting`。渲染器按 `environment_lighting` 查找 → 找不到 → `authored_lights == []` → **静默回退**。

**关键点：这个失败是静默的。** 渲染照常完成，只是光照是错的。若不做仪表化排查，会直接产出 18 条违反铁律四的视频。

## 2. 重大缺陷二：补丁地板与真实地板提取

### 2.1 背景

`maps.yaml` 的 `replicad_apartment_floor_pinned` 区域原先用 **`bounds_xy` 盒体**作为碰撞支撑面，即一块 1.7 × 1.7 m = 2.89 m² 的"补丁地板"。用户要求删除，改用**场景自带地板**。

### 2.2 第一次提取失败（原因已查明）

第一次按"朝上的面 且 面中心 z ∈ [0, 0.05)"筛选，得到 202 面 / 81.61 m²。但**实测发现物体停在错误高度**：

```
期望静止中心 z = 0.08302   (position[2] 0.0007 + support_height 0.08232)
实测静止中心 z = 0.15386   -> 高了 7.1 cm
supported_fraction = 0.0123   (要求 >= 0.9)
```

射线检测定位到原因：在放置点 (0.65, -2.15) 射线命中 **z = 0.084**。

**根因**：按**面中心**筛选会漏掉**跨越高度变化的大三角形**——它的中心 z 很低，但表面在其他位置隆起。这些三角形把家具/台阶/墙脚的几何带进了"地板"。

### 2.3 正确判据与重新提取

新判据：**三个顶点全部**在离地板 1 cm 以内（`max(vz) < 0.010`）且面法线朝上（`n.z > 0.9`）。

```
FLAT faces kept: 94 of 132091
FLAT area 84.68 m^2
```

产出 `collision/surfaces/replicad_apartment_floor.obj`：237 顶点 / 94 面 / 8,434 bytes。

逐轴包围盒验证（这次是正确的分轴打印）：

```
x: [-2.6766, 4.5798]  span=7.2564
y: [-8.1644, 4.8289]  span=12.9933
z: [-0.0416, 0.0007]  span=0.0424
```

**z 上限 = 0.0007**，即地板平面本身；下限 -0.0416 是板厚。**不再有 0.140 的隆起几何。**

### 2.4 修复后实测（关键证据）


### 2.5 放置区域（placement）与碰撞（collision）的正确区分

这是本轮理清的一个**重要概念区分**：

| 用途 | 来源 | 尺寸 |
|---|---|---|
| **碰撞**（物体停在什么上） | `collision: type: mesh` → 场景真实地板 mesh | **84.68 m²** |
| **放置**（物体能生成在哪） | `bounds_xy` | 需另测 |

`SurfaceSpec.contains_xy()` 同时检查 `bounds_xy` 与 `polygon_xy`，而 `SurfaceSampler` 只用 `bounds_xy`。因此放置范围必须单独测定。

### 2.6 放置区域实测（射线检测）

用射线从上方扫描地板足迹（0.10 m 网格，8500 点），"该点为地面"的判据是**首次命中即地板本身（z < 0.05）**：

即放置区 5.1 × 3.7 m = **18.87 m²**（原为 1.7 × 1.7 m = 2.89 m²，扩大 6.5 倍），且**每一点都经过射线验证为真实空地**。

## 3. 物理参数关键发现：GSO 物体不能"滚"，只能"滑"

### 3.1 现象

rolling 场景在真实地板上反复失败：

```
v0 = 0.0845 m/s   (极慢)
mass = 0.001481 kg  (1.5 克)
friction = 0.36
travel_distance = 0.068 m   (要求 0.169 m)
supported_fraction = 0.012
```

### 3.2 根因

学长的 `rolling` 配置是**为球设计的**：球**滚动**时，侧向摩擦**不制动**它（`rolling_friction: 0` 时球可以无限滚下去），摩擦只维持滚动接触。

**我们的 GSO 物体是罐子/盒子/花盆——凸包，无法滚动，只能滑动。** 对滑动体，侧向摩擦就是**完整的制动力**：

```
减速度 = mu * g = 0.36 * 9.81 = 3.5 m/s^2
初速 = 0.0845 m/s
停止时间 = 0.0845 / 3.5 = 0.024 s   <- 不到一帧 (1/16 = 0.0625 s)
```

### 3.3 摩擦扫描实测

在真实地板上扫描摩擦系数（v0 = 0.20 m/s，81 帧）：

| mu | v0 | v40 | v80 | travel | rel_change | 单调 |
|---|---|---|---|---|---|---|
| 0.000 | 0.2000 | 0.2000 | 0.2000 | **1.000** | **0.0000** | True |
| 0.010 | 0.1968 | 0.0609 | 0.0006 | 0.358 | 0.9991 | False |
| 0.020 | 0.1940 | 0.0004 | 0.0004 | 0.176 | 0.9998 | False |
| 0.030 | 0.1913 | 0.0015 | 0.0007 | 0.112 | 0.9996 | False |
| 0.050 | 0.1849 | 0.0007 | 0.0008 | 0.062 | 0.9992 | False |
| 0.080 | 0.1770 | 0.0001 | 0.0003 | 0.035 | 0.9996 | False |

**关键结论**：即使 mu = 0.01 也会让物体在 5 秒内停下。要满足"匀速"（速度变化 ≤ 25%），**mu 必须为 0**。

这在物理上是**正确的**：`mu = 0` = 无摩擦支撑面上的匀速滑行，即**牛顿第一定律**，是"匀速运动"最纯粹的演示。这与学长自己的 `rolling` 配置所做的理想化（`rolling_friction: 0, spinning_friction: 0`）是**同一类理想化**，只是我们的物体滑动而非滚动，故需扩展到侧向摩擦。

### 3.4 代码改动（最小且向后兼容）

为让场景配置能覆盖接触参数，给 `base_physics()` 增加**一个可选参数**：

```python
def base_physics(rng, asset, physics: dict | None = None):
    overrides = physics or {}
    return (
        uniform(rng, overrides.get("mass_range", asset.mass_range)),
        uniform(rng, overrides.get("friction_range", asset.friction_range)),
        uniform(rng, overrides.get("restitution_range", asset.restitution_range)),
    )
```

三个既有场景的调用点同步改为 `base_physics(rng, asset, physics)`。**默认行为完全不变**（不传 `physics` 时与原实现逐字节一致）。

> **这仍然没有规定轨迹。** 采样值原样送入求解器，Bullet 积分出什么就是什么。

## 5. 阻尼运动（运动 #7）的实现

### 5.1 为什么必须用阻尼而非摩擦

两者是**不同的物理规律**：

| 机制 | 速度规律 | 到达零 |
|---|---|---|
| 库仑摩擦 | `v = v0 - mu*g*t`（线性） | 有限时间 |
| 阻尼 | `v = v0 * exp(-k*t)`（指数） | 渐近 |

要让画面呈现**真正的阻尼**，必须令 `lateralFriction = 0`，只保留 `linearDamping`。

### 5.2 阻尼可用区间（实测）

`changeDynamics` 的阻尼参数**确实生效**（V1.0 曾记录它"静默无效"，那是 `useMaximalCoordinates` 下的旧结论，当前后端不适用）：

| k | v0 | v20 | v40 | v80 | x_end | 判定 |
|---|---|---|---|---|---|---|
| 0.0 | 1.0000 | 1.0000 | 1.0000 | 1.0000 | – | 无效果 |
| 0.2 | – | – | – | – | – | 干净衰减 |
| 0.4 | – | – | – | – | – | 干净衰减 |
| 1.2 | 0.0000 | 0.0000 | 0.0000 | 0.0000 | – | **一帧内停止** |
| 3.0 | 0.0000 | 0.0000 | 0.0000 | 0.0000 | – | **一帧内停止** |

**结论**：可用区间约 **0.1 – 1.0**。k ≥ 1.2 会让物体在第一帧就停住。

最终配置 `damping_range: [0.18, 0.30]`（x1.5 变体最高 k = 0.45）。

> 初版用 `[0.25, 0.45]`，x1.5 时 k = 0.597，尾部衰减比降到 0.011，触发 `over_damped` 门限。降至 `[0.18, 0.30]` 后 6/6 通过。

### 5.3 代码改动清单（5 处，均为最小改动，未触碰 `third_party/`）

| # | 文件 | 改动 |
|---|---|---|
| 1 | `src/physim/scenarios/__init__.py` | `ScenarioSample` 增加 `linear_damping` / `angular_damping`，默认 0.0 |
| 2 | `src/physim/physics/pybullet_backend.py` | `changeDynamics` 传 `linearDamping` / `angularDamping` |
| 3 | `src/physim/scenarios/__init__.py` | 工厂注册 `"damping"` |
| 4 | `src/physim/validation/__init__.py` | 新增 `validate_damping` + 派发 |
| 5 | `src/physim/scenarios/damping.py` | **新文件**，场景采样 |

**向后兼容性**：`linear_damping` / `angular_damping` 默认 0.0，且后端用 `getattr(sample, ..., 0.0)` 读取，因此**三个既有场景的行为逐字节不变**。V3.3 冻结的室内场景与转盘资产**未受影响**。

### 5.4 `validate_damping` 的判据

阻尼是**指数**衰减，不能用摩擦的线性判据。四项检查：

1. **必须真的衰减**：`decay_ratio <= max_decay_ratio`（0.60），否则 `insufficient_damping`
2. **不能是"假停"**：`decay_ratio >= min_decay_ratio`（0.03），否则 `over_damped`
3. **单调衰减**：允许 3 帧以内的接触抖动，否则 `non_monotonic_decay`
4. **与解析解吻合**：`|实测衰减比 - exp(-k·T)| <= 0.45`，否则 `damping_decay_mismatch`

> 第 4 项是**对求解器行为的测量**，不是预设轨迹。偏差过大意味着运动不是由阻尼产生的。

## 6. 抛体运动（运动 #4）的实现：零代码改动

`free_fall.py` 第 52–58 行**已经支持水平初速**（读取 `horizontal_speed_range`），因此抛体**只需一份 yaml**。

### 6.1 放置失败与修正（实测）

初版设 `horizontal_speed_range: [1.50, 3.00]`，三个物体全部：

```
ERROR ValueError: Surface cannot contain the requested rolling trajectory
```

**根因**（`free_fall.py` 第 64–72 行）：

```python
support_height = asset.support_height + drop_height
travel_distance = horizontal_speed * duration
```

采样器把**整个 5.0625 秒的水平行程**外加**落差**都算作放置边距。1.5–3.0 m/s 意味着预留 **7.6–15.2 m** 行程，而放置矩形只有 5.10 × 3.70 m。

**这是场景的固有设计**（适配学长的短时长小球），因此本管线内的抛体必须按房间尺寸缩放：

```
reserved_travel = v * 5.0625 <= ~2.0 m   ->   v <= ~0.40 m/s
```

改为 `horizontal_speed_range: [0.30, 0.40]`、`edge_margin: 0.20` 后 **3/3 PASS**。

> 物理解释：0.35 m/s 在约 0.45 s 飞行时间内横移约 0.16 m，同时下落约 1 m，轨迹是清晰的抛物线；落地后水平分量转为滑行。**这是在本房间尺度与 81 帧时长下诚实呈现抛体的唯一方式**——更快的投掷无法放进客厅。

## 6.5 重大缺陷三：相机门限过严导致渲染失败（已修复）

### 6.5.1 现象

T1 首轮渲染中，第 1 条（rolling / whey_protein_vanilla）**成功**（23 分钟，81 帧 + mp4，`valid=True`），但第 2、3 条在 **5 秒内**失败：

```
ValueError: A static camera cannot fit the complete trajectory while keeping the
largest object visible: projected fraction 0.0907, minimum 0.1000
```

**注意：物理校验是通过的**，失败发生在**相机求解**阶段（`camera/__init__.py:155`）。

### 6.5.2 根因

相机取景距离取三者最大：

```python
distance = max(fit_distance, min_size_distance, min_distance)
```

其中 `fit_distance` 由 `content_width` 决定，而

```python
content_width = horizontal_extent + max_object_extent * (padding)
object_frame_fraction = max_object_extent / frame_width
```

**轨迹越长 → `content_width` 越大 → 相机退得越远 → 物体在画面中越小。**

我设的 `min_object_frame_fraction: 0.10` 比学长自己三份配置里一致使用的 **`0.03`** 严格了 **3.3 倍**，于是长轨迹的物体投影占比 0.0907 就触发了门限。

### 6.5.3 修复

将全部 `*_gso.yaml` 的 `min_object_frame_fraction` 统一放宽到学长验证过的 **0.03**：

| 文件 | 原值 | 新值 |
|---|---|---|
| `rolling_gso.yaml` | 0.10 | 0.03 |
| `constant_force_gso.yaml` | 0.10 | 0.03 |
| `free_fall_gso.yaml` | 0.15 | 0.03 |
| `damping_gso.yaml` | 0.10 | 0.03 |
| `projectile_gso.yaml` | 0.03 | 0.03（已符合） |

> **重要**：`min_object_frame_fraction` **只出现在检查中**（`max_size_distance`），**不参与 `distance` 的计算**。因此放宽该门限**不会改变已通过片段的取景**，已渲染的第 1 条仍然有效。

### 6.5.4 流程改进：预检必须包含相机

首轮预检（`preflight9.sh`）只做 `sample → simulate → validate`，**漏掉了相机步骤**，所以第 2、3 条"预检通过"却在正式运行时失败。

```python
camera_variant = reference_variant(config)          # 取景的是最大变体

cam = perpendicular_camera(

    max_object_extent=object_extent(asset),
)
```
