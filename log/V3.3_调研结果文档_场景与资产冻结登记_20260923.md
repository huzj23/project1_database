### 1.3 ⚠️ 本次唯一的改动：碰撞面（**但见 §9：对求解器无效**）

> **重要**：本节记录的 `asset.yaml` 改动**经复核确认不参与求解器支撑面的构建**。
> 求解器只读 `maps.yaml` 的 region。详见 **§9 重大更正**。

**改造前**（手工放置的小补丁）：

```yaml
collision:
  type: box
  center: [2.700000, -1.600000, -0.049268]
  half_extents: [0.500000, 2.700000, 0.05]      # 1.0 × 5.4 m = 5.40 m²
```

**改造后**（场景自带地板）：

```yaml
# The scene ships its own floor slab: x=[-2.677,4.580] y=[-8.164,4.829]
# = 94.28 m^2 at z~0.  A single box spanning that footprint is geometrically
# exact for the flat living area and replaces the earlier 5.4 m^2 patch that
# covered only 5.7% of the real floor.
collision:
  type: box
  center: [0.9515, -1.6675, -0.049268]
  half_extents: [3.6285, 6.4965, 0.05]          # 7.26 × 12.99 m = 94.29 m²
```

| | 改造前 | 改造后 |
|---|---|---|
| 覆盖面积 | 5.40 m² | **94.29 m²** |
| 占真实地板 | **5.7%** | **100%** |
| 物体依附于 | 我们加的补丁 | **场景自带地板** ✅ |

**为何用 box 而非 mesh**：地板主起居区平整，一个 box 在几何上**精确等价**，
且远轻于 36 三角形 mesh 的凸分解。楼梯踏步高于地板，不与 box 冲突。

### 2.3 物理驱动四步（**缺一不可**）

```
转盘 = 动力学体（static=False）        ← 必须，见陷阱 1
每物理步：
  1. resetBasePositionAndOrientation  钉住位置，朝向原样传回
  2. resetBaseVelocity(0, ω ẑ)        当"电机"，重设角速度
  3. stepSimulation()                 求解器自己算摩擦耦合
  4. 按 physics_fps/video_fps 次子步   否则慢 10 倍
```

### 2.4 实测验证

| 工况 | 结果 |
|---|---|
| ω = 0.50 rad/s | 滑移比 **0.99**（物体 83.6° / 转盘 84.2° / 理论 85.9°），半径恒定 **0.300 m** |
| ω = 0.90 rad/s | 半径恒定 **0.170 m**，角度线性递增 |

**最新一次（ω=0.9，转盘置于桌面）**：

| 帧 | 半径 | z | 角度 |
|---|---|---|---|
| 00 | 0.170 m | 0.8566 | +2.1° |
| 08 | 0.171 m | 0.8566 | +23.5° |
| 16 | 0.171 m | 0.8566 | +44.1° |
| 24 | 0.171 m | 0.8565 | +64.5° |

→ z 恒定（**无掉落、无穿模**）、半径恒定（**绕轴公转**）、角度线性（**匀角速度**）。
4 帧真正不同（118–134 万像素变化）。

### 2.5 ❌ 勿用清单（6 条陷阱，全部实测踩过）

| # | 陷阱 | 后果 |
|---|---|---|
| 1 | `static=True` | Kubric 传 `useFixedBase=True`，**转盘被焊死**，永远不转 |
| 2 | `changeDynamics(mass=0)` | 物体在 PyBullet 中**变静态体**，设了速度也不动 |
| 3 | 每步重置朝向为单位四元数 | 转盘**视觉上不转**（物体仍会爬行） |
| 4 | 每步"传送"转盘位姿 | 接触流形被反复重置，摩擦**完全无法建立**（滑移比 0.00） |
| 5 | 按视频帧步进 | 每帧只推进 1/240 s，**慢 10 倍** |
| 6 | 半径 0.55 m | 盘**悬在桌外** |

### 2.6 关键帧铁律（**最重要的一条**）

> **Blender 不会自己动。** 必须把 PyBullet 轨迹逐帧转录为关键帧：

```python
for f, (pos, quat) in enumerate(trajectory):
    bpy.context.scene.frame_set(f)
    obj.location = pos
    obj.rotation_mode = "QUATERNION"
    obj.rotation_quaternion = (quat[3], quat[0], quat[1], quat[2])
    obj.keyframe_insert("location", frame=f)
    obj.keyframe_insert("rotation_quaternion", frame=f)
```

**实测后果**：未转录时 **4 帧 PNG 的 MD5 完全相同**（`DA6B7B8E482F64C9` ×4，
像素差 0）。转录后 f08 vs f00 变化像素 **1,240,023**。

### 5.2 ⚠️ 方法边界（必须记录，避免重复踩坑）

**HDRI 是位于无穷远的等距柱状全景图**：

- 下半部分**就是**地面影像，地平线在 ≈0° 仰角
- **没有视差**，地面透视是**烘焙进去的**
- 因此**无法与任何真实三维平面做几何对齐**——这是**方法边界，不是参数问题**

**实测证据**（`ballawley_park`，相机 h=1.15 m，vFOV 32.27°，1280×720）：

| 项 | 值 |
|---|---|
| HDRI 地平线行 | **197** |
| 我们的可见平面首次绘制行 | `vis_14m` → 449；`vis_120m` → 349；`vis_800m` → 333 |
| 覆盖行数 | 271 / 371 / 387 |
| 影子捕捉平面改动行数 | **7 行**（仅阴影本身） |

> **结论**：平面**遮住了 HDRI 自带地面 136–252 行**——这才是用户看到的"覆盖"，
> **不是亮度不匹配**。此前反复调平面尺寸与亮度是**可证明无效的**
> （平面尺寸 +50.7/+51.9/+44.2 步长在 14/120/800 m 下几乎不变；
> 品红探针显示平面覆盖下半画面 **99.38%**）。

### 5.3 已采纳的处置

**合成平面已删除**。用户质疑正确："那块平面是我们自己加的，不是场景提供的。"
现室外画面中唯一的地面即 **HDRI 自带地面**。

**两种方案**（`outcomes/_reformed/OUTDOOR_REFORMED.png`）：

| 方案 | 说明 |
|---|---|
| `hdri_only` | 完全没有合成地面，物体悬于静止高度（**无碰撞面**） |
| `shadow_only` | 平面对相机**不可见**但接收接触阴影（`is_shadow_catcher=True`） |

> **诚实取舍**：不能同时做到"没有平面"和"物体有东西可站"。
> 室外若需真实物理，应接**场景自身几何**的碰撞面，而非手工平面。

### 5.4 ⚠️ 室外不参与本轮仿真

**原因**：室外**没有可交互的三维地面几何**（只有 HDRI 图像），
无法满足铁律一（真求解器需要真实接触面）。

## 9. ⚠️ 重大更正：asset.yaml 的碰撞改动**对求解器无效**

### 9.1 发现

审查物理后端时发现：**`asset.yaml` 的 `collision` 块根本不参与支撑面的构建。**

```python
# src/physim/physics/pybullet_backend.py:36-76
surface = map_spec.surface(sample.surface_id)
if surface.collision_simulation_path is not None:
    support_body = kb.FileBasedObject(...)      # 路径 A：用 region 的 mesh URDF
else:
    xmin, xmax, ymin, ymax = surface.bounds_xy  # 路径 B：用 region 的 bounds_xy
    support_body = kb.Cube(...)
```

支撑面**只**来自 `maps.yaml` 的 **region**（`bounds_xy` 或 `collision.simulation`），
与 `asset.yaml` 的 `collision` 无关。

`MapSpec.collision_center` / `collision_half_extents` 确实被**读取**
（`maps/__init__.py:146-147`），但**在全仓库中再无任何消费者**：

```
grep -rn 'collision_half_extents|collision_center' src/ scripts/ --include='*.py'
  maps/__init__.py:85,86,146,147   <- 只有定义与赋值
  (无其他文件)
```

### 9.2 实测验证

```
MapSpec.replicad_apartment
  collision_center       = (0.9515, -1.6675, -0.049268)
  collision_half_extents = (3.6285, 6.4965, 0.05)
  -> asset.yaml footprint= 94.29 m^2        <- 我们改的值

  surface replicad_apartment_floor_pinned
    bounds_xy                = (0.15, 1.85, -5.15, -3.45)
    collision_simulation_path= None
    -> support box = 1.700 x 1.700 m = 2.89 m^2
    ==> 求解器实际使用 2.89 m^2，不是 asset.yaml 的 94.29 m^2
```

### 9.3 结论与更正

| 项 | 之前我以为 | **实际** |
|---|---|---|
| 改 `asset.yaml` collision 的作用 | 物体落在 94.29 m² 地板上 | **无效**——求解器不读它 |
| 求解器实际的支撑面 | — | `maps.yaml` region 的 `bounds_xy` = **2.89 m²** |
| 我此前的"改造成功" | 5.40 → 94.29 m² | **只在数值上成立，未生效** |
| 我此前撤销的 maps.yaml 改动 | "越界的多余改动" | **那才是真正生效的那一处** |

> **必须向用户说明**：我此前汇报的"物体现在落在场景自带的 94.29 m² 真实地板上"
> **是不准确的**。渲染图看起来正确，是因为**物体本来就落在 2.89 m² 的支撑盒内**，
> 而那 2.89 m² 位于公寓地板之上——**视觉上无差别，但支撑面并未变成整个地板**。
>
> **我撤销 maps.yaml 改动这一步，恰好把唯一生效的开关留在了原值。**
> 这不是坏事（保持了此前已验证的行为），但**我给出的解释是错的**，必须更正。

### 9.4 正确的改法（两条路，待用户选择）

| 路径 | 做法 | 面积 | 代价 |
|---|---|---|---|
| **B（简单）** | 扩大 `maps.yaml` region 的 `bounds_xy` | 任意 | 一行改动；但 box 是矩形，可能覆盖到家具 |
| **A（正确）** | 按学长 `classroom` 桌面的模式，声明 `collision: type: mesh` + 用 `generate_environment_surface_collision.py` 从 `scene.blend` 提取**地板 slab 的静态 URDF** | 精确贴合 94.28 m² 真实地板 | 需提取 + 登记 + 重测 |

**路径 A 的模板已在仓库中**（`classroom_student_desk_a`）：

```yaml
collision:
  type: mesh
  mesh: collision/surfaces/<name>.obj
  simulation: collision/surfaces/<name>.urdf
  source_components: [...]
  triangles: 1288
  max_triangles: 2048
  mesh_sha256: ...
```

**地板 slab 已定位**：`Mesh.561`，91 顶点 / **36 三角形**（远低于 2048 上限，
提取成本极低）。提取工具 `scripts/generate_environment_surface_collision.py`
支持 `--source/--component/--object/--output/--urdf-output/--max-faces`。

`maps.yaml` 中 `table_top` 的现成模板在 `classroom` 段（第 41 行起），
