# V4.1 调研结果文档 — 碰撞体生成脚本对 OBJ 输入的坐标系缺陷

- 日期：2026-09-23
- 范围：`physics-video-sim-main/scripts/generate_collision_mesh.py`（**mentor 上游脚本，我们未做任何修改**）
- 触发场景：把 GSO 的 OBJ 资产（`special_plush_elephant`）按资产规范重新生成 ≤512 面碰撞体
- 结论：该脚本对 **OBJ 输入**会输出一个相对 visual 绕 X 轴旋转 +90° 的碰撞体；对 **GLB 输入**完全正确

---

## 1. 缺陷本身

脚本两处坐标系处理不一致（行号为仓库当前版本）：

**导入（第 25-38 行）** —— OBJ 分支没有传任何轴向参数：

```python
def _load(source: Path) -> None:
    ...
    elif suffix == ".obj":
        bpy.ops.import_scene.obj(filepath=str(source), use_split_objects=False)
```

Blender 的 `bpy.ops.import_scene.obj` 默认约定是 `axis_forward='-Z', axis_up='Y'`（Y-up），
导入一个 Z-up 的 OBJ 时会给对象本体写入一个 **绕 X 轴 +90°** 的旋转
（实测 `rotation_euler = (90°, 0, 0)`，`matrix_world` 为 `[[1,0,0],[0,0,-1],[0,1,0]]`）。

**导出（第 134-141 行）** —— 导出时声明的是 Z-up：

```python
    bpy.ops.export_scene.obj(
        filepath=str(output),
        use_selection=True,
        use_materials=False,
        use_triangles=True,
        axis_forward="Y",
        axis_up="Z",
    )
```

`axis_forward="Y", axis_up="Z"` 对 Z-up 的 Blender 场景是**恒等变换**，不会抵消导入时写入的旋转。
另外，脚本取点是 `mesh.matrix_world @ vertex.co`（第 91-95 行），即**带上了**那个 +90° 旋转，
所以旋转被烘进了输出顶点。

**净效果**：对 OBJ 输入，`输出 = Rx(+90) · 原始文件坐标`，即 `(x, y, z) -> (x, -z, y)`。
对 GLB 输入，glTF 导入器给出的是恒等旋转，因此导出也是恒等 —— **GLB 路径没有问题**，
mentor 自己的 `food_lime` / `food_apple` / `food_lychee`（均为 `visual/model.glb`）不受影响。

## 2. 实测证据

### 2.1 脚本直接输出（大象，`--target-faces 512`）

| 指标 | 脚本原始输出 | visual（真实文件） | 偏差 |
| --- | --- | --- | --- |
| dims (x,y,z) | 0.267970, 0.207368, 0.220576 | 0.267932, 0.220669, 0.207446 | y/z 互换 |
| `support_height` | **0.115146** | **0.073659** | **+56.3%** |
| `bounding_radius` | 0.166734 | 0.166746 | 一致（球半径与旋转无关） |
| 三角面 | 512 | — | 符合上限 |

`support_height` 高出 56%，远超任务书设定的"几个百分点"容忍度。

把脚本输出做 `Rx(-90)`（`(x,y,z) -> (x,z,-y)`）后，AABB 变为
`min=[-0.132426,-0.115146,-0.073611] max=[0.135544,0.105430,0.133757]`，
与 visual 原始 AABB `min=[-0.132393,-0.115208,-0.073659] max=[0.135539,0.105461,0.133787]`
逐轴吻合 —— 反证了旋转关系成立。

### 2.2 运行时 visual 到底在哪个坐标系（决定性证据）

不看 API 默认值，直接用**已经渲染完成的 dataset** 反投影测真值：
`datasets/turntable_carry/seed-005001/x1`，从 depth 帧反投影到世界坐标，
量取 actor 顶部相对转盘顶面（z = 0.7804）的高度。

| 帧 | actor 位置 z | 实测顶部高度 | 若 visual 为 raw 帧的预测 | 若 visual 被 Rx(+90) 的预测 |
| --- | --- | --- | --- | --- |
| 0 | 0.8544 | **0.2064** | 0.2078 | 0.1795 |
| 40 | 0.8521 | **0.2049** | 0.2055 | 0.1772 |
| 80 | 0.8496 | **0.2038** | 0.2030 | 0.1747 |

（raw 预测 = `actor_z + 0.133787 − 0.7804`；旋转预测 = `actor_z + 0.105461 − 0.7804`）

实测与 raw 帧预测差 ~1 mm，与旋转帧预测差 ~27 mm。
**结论：运行时 visual 处于原始文件坐标系（Z-up，未旋转）。**
这与 Kubric `kubric/renderer/blender.py` 第 611 行只在 GLB/gltf 分支施加固定旋转、
OBJ 分支不施加的行为一致。

因此脚本原始输出若直接安装，会让碰撞体相对 visual 转 90°，同时 `support_height` 偏高 56%。

## 3. 实际影响

1. **碰撞体与 visual 不同坐标系**：违反资产规范"碰撞 mesh 必须从已经完成米制缩放、居中和
   变换烘焙的 visual 生成，保持相同原点、朝向和尺度"。
2. **`support_height` 偏高 56%**（0.115146 vs 0.073659）：直接决定落地高度与滚动角速度尺度，
   会把 actor 悬空或让滚动标定整体失准。
3. 只影响 OBJ 资产。本项目里受影响的只有 GSO 系列（`visual/model.obj`）；
   `food_*`、`sphere_*`、`special_coffee_cup` 都是 GLB，**不受影响**。

## 4. 本次处理方式

- **未修改** `scripts/generate_collision_mesh.py`（这是 mentor 的工具，我们只新增资产）。
- `special_plush_elephant`：先用脚本原样生成（512 面），再对生成的 mesh 施加精确逆变换

  脚本的原始输出保留在 `tmp/zz_coll_final/raw_model.obj` 供比对。

  `bounding_radius = 0.166734`，三角面 512。

## 5. 建议的上游修法（供 mentor 参考，我们未实施）

任选其一即可，**推荐第 1 种**（最小改动、对 GLB 无影响）：

1. **导入时显式声明 OBJ 的坐标系**，与导出对称：

   ```python
   elif suffix == ".obj":
       bpy.ops.import_scene.obj(
           filepath=str(source),
           use_split_objects=False,
           axis_forward="Y",
           axis_up="Z",     # 与 _load 的导出约定一致，导入即恒等
       )
   ```

2. **导出时按输入格式选择约定**：对 OBJ 输入用 `axis_forward="-Z", axis_up="Y"`
   把导入写入的 +90° 转回去（等价于对 GLB 保持现状）。

3. 或者在取点后统一做一次坐标系归一：以 `source.suffix` 判断是否需要 `Rx(-90)`。

无论哪种，都建议在脚本里加一条断言：生成后的碰撞体 AABB 与 visual AABB 逐轴对齐
（本缺陷正是靠这条检查发现的）。
