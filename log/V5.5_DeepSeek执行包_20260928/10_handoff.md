## 2. 每次attempt最小记录

```json
{
  "schema_version": "v55.execution.1",
  "stage": "08",
  "run_id": "实际唯一ID",
  "attempt_id": "a001",
  "scene_id": "从配置读取",
  "seed": 550001,
  "changed_parameter": "明确单一变化或initial",
  "reason": "为何改变",
  "config_sha256": "实际hash",
  "trajectory_sha256": "运行后实际hash",
  "passed": false,
  "status": "not_started",
  "failure_reasons": [],
  "outputs_absolute": [],
  "tmux_session": null,
  "exit_code": null
}
```

此JSON是模板，不是当前已执行报告。实现中将未运行/未知结果留null或明确状态，不能使用假hash填满。没有进程退出码就不能声称完成。日志不包含凭据文件内容和他人进程参数。

## 3. 状态与恢复规则

- 一个阶段只有所有硬门槛和证据齐全才是passed。
- 子阶段物理通过但渲染未完时分别记录，不把整关标passed。
- 上次会话停止时先查tmux/PID/日志尾部和status，再决定续跑；已有作业不能重复启动。
- 不自动清除失败目录。既有输出校验通过可复用；配置或输入hash变化则建立新attempt。
- 若source/runtime/代码改变，标明哪些既有验证需要重跑，不能让旧PASS覆盖新实现。
- 遇到两轮物理搜索失败时写诊断记录：几何、物性、能量、碰撞、相机哪一项失败，下一轮选择基于证据。
- 仅时间长不是失败；tmux日志持续增长则继续监控并更新用户。停止只针对本任务确定的PID，不发全局kill。

## 4. 用户汇报模板

```text
本轮完成：<实际阶段和可见结果>
视频：<本地可播放链接>
物理证据：<接触顺序、通过比例、无触发/断链结果>
限制：<真实近似与未完成项>
Git：<提交与推送状态>
下一步：<已经继续/具体阻塞>
```

用户问进度时给出结果/正在做的工作，然后继续执行授权范围；不要把询问进度当作取消任务。用户更新偏好时保持其他目标不变，按最新要求调整配置并记录。

## 5. Codex审查时的必看项

交回策划者检查：实际源码diff、源/配置hash、连续视频、全部传播事件、两项因果对照、dt敏感性、无删除证明、资源日志、失败次数与选择理由。策划审查不取代执行者自己的验证，也不要求每个小修改都等待审查才能继续。
